# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository shape

CasaClean is a cleaning-service booking platform split into two **independent npm packages** (there is no root `package.json` or workspace tooling — install/run each side separately):

- `server/` — Express 5 + Mongoose 9 REST API (CommonJS). Cookie/JWT auth, Google OAuth, email verification.
- `client/` — React 19 SPA built with Vite (ESM, JavaScript, **no TypeScript**). Marketing site + booking wizard + admin panel.
- `api-testing/` — QA test plan (markdown per resource) and a ready-to-import `CasaClean.postman_collection.json`. The Postman collection auto-captures the `lt` auth cookie and ids between requests; use it to exercise the API end-to-end.

Deep references already exist — read them before large changes instead of re-deriving:
- `client/FRONTEND.md` — exhaustive front-end architecture (provider graph, routing, design system, i18n, SEO, booking wizard). `client/README.md` is the shorter version.
- `api-testing/README.md` + `api-testing/00-setup.md` — endpoint-by-endpoint behavior and the admin-bootstrap procedure.

## Commands

**Server** (`cd server`):
- `npm install`
- `node app.js` — start the API. There is **no `start`/`dev` script** despite what `api-testing/00-setup.md` says (`npm start` will fail with "Missing script: start"). Use `node app.js`, or run nodemon yourself for reload.
- `npm test` — Jest (`--runInBand`) over `server/tests/{unit,integration}`; integration suites boot an in-memory MongoDB and mock Stripe + email (`tests/setup/testEnv.js`). Also `npm run test:watch` / `test:coverage`. For anything not covered there, verify against `api-testing/` manually or via the Postman collection.

**Client** (`cd client`):
- `npm install`
- `npm run dev` — Vite dev server
- `npm run build` / `npm run preview`
- `npm run lint` — ESLint
- `npm test` — Vitest (`vitest run`) over the colocated `*.test.js` files (API payload mappers, booking maths/validation, service localization). Also `npm run test:watch` / `test:coverage`.

Both sides need a `.env` (copy from each `.env.example`). The server **refuses to boot** with missing/weak config (see below), so populate `MONGO_URI`, `JWT_SECRET` (≥32 chars, not a placeholder), `JWT_EXPIRES_IN`, `CLIENT_URL`, `SERVER_URL`, `PORT` before starting. To create the first admin: sign up, verify the email, then flip that user's `role` to `"admin"` directly in MongoDB.

## Backend architecture

### Request pipeline (order is load-bearing — see `server/app.js`)
`assertEnv()` (fail-fast on bad config) → `helmet` → Stripe webhook (raw body) → `/healthz` → `compression` → `express.static('/uploads')` → CORS allow-list (`CLIENT_URL` only, `credentials:true`) → `globalLimiter` → `passport.initialize()` → `express.json({limit:'4mb'})` + `cookieParser` → `csrfGuard` → `sanitizeMongo` → routers (`/api/v1/{auth,city,service,booking,special-request,review,subscription,invoice,contact}`) → `/*splat` 404 → Sentry error handler → `globalErrorHandler` (must be last).

### File uploads
A service's cover image is uploaded via **multer** (`middlewares/upload.middleware.js`) to `server/uploads/services/` (git-ignored, recreated at boot by `ensureUploadDirs()`) and served read-only from `/uploads` — mounted *before* the rate limiter so image fetches don't burn API quota, with `Cross-Origin-Resource-Policy: cross-origin` so the SPA on another origin can render them. `utils/upload.util.js` owns the paths and the traversal-safe delete.

Documents store the **relative** path (`/uploads/services/<random>.png`); the client resolves it against the API origin (`services/api/assets.js` `assetUrl()`). Filenames are random + an extension derived from the MIME type — never from `originalname`.

`POST /service` and `PATCH /service/:id` accept **either** JSON **or** `multipart/form-data`; multer no-ops on JSON. On multipart, `coerceMultipart` (`middlewares/multipart.middleware.js`) re-types the flattened string fields (numbers/booleans/JSON-encoded arrays and objects, the latter carrying the `translations` map) so the one strict Zod schema validates both encodings. `sanitizeMongo` is re-run inside the service router because the app-level pass happens before multer populates `req.body`. A router-level error handler unlinks `req.file` on any downstream failure so nothing is orphaned; the controller deletes the previous file after a successful replace and on service delete.

### Routes and background jobs

- The application mounts recurring-subscription routes at `/api/v1/subscription` and invoice routes at `/api/v1/invoice`.
- Recurring subscription charges run through `node-cron`. Jobs start only inside
  `start()` after `app.listen` when `server/app.js` is run directly, so requiring
  the app (including from tests) has no cron side effects. Shutdown calls
  `stopJobs()` before closing the listener and database; the charge sweep remains
  exported for controlled verification.

### Per-resource MVC layering
Each resource follows the same vertical slice, named by suffix: `routers/x.router.js` → `validations/x.validation.js` (Zod) → `controllers/x.controller.js` → `models/x.model.js`.

- **Routers** wire middleware in order: rate limiter → `protect`/`restrictTo` → `validate(schema)` → controller. `restrictTo("admin")` always comes *after* `protect` (which populates `req.user`). Declare literal routes (e.g. `/my`) before dynamic ones (`/:id`).
- **`validate(schema)`** (`middlewares/validate.middleware.js`) runs `schema.safeParse(req.body)` and **replaces `req.body` with the parsed data**. Zod schemas use `.strict()` so unknown fields are rejected.
- **Controllers** are wrapped in `catchAsync` (any throw/rejection → `next(err)`). They **never spread `req.body`** — every write explicitly whitelists fields to block mass-assignment of server-managed fields (`user`, `role`, `status`, payment ids). Throw `new AppError(message, statusCode, details?)` for operational errors.
- **`globalErrorHandler`** (`controllers/error.controller.js`) is the single response formatter. It normalizes Mongoose `CastError`/`ValidationError`, Mongo `11000` duplicates, and JWT errors into `AppError`s. Verbosity is environment-gated.

### Response envelopes
- Success: `{ status: "success", message, data: { ... } }` (list endpoints add a count field, e.g. `bookingCount`).
- Error: `{ success: false, status, message }` (dev mode also includes `error`, `stack`, `errors`).

### Auth & security model (the distinctive part of this codebase)
- **Session** = httpOnly cookie named `lt` holding a JWT. The JWT payload carries **only the user id, never the role** — `protect` re-loads the user from the DB each request and authorizes on the live `role`, so a token can't carry a stale/forged role.
- **`utils/env.util.js` is the single source of truth for environment posture and is FAIL-SECURE**: `isProduction` is true for *any* `NODE_ENV` that isn't explicitly `dev`/`development`/`test`. Cookie `Secure`/`SameSite=None` flags and error verbosity key off this — an unknown env value gets the safe production behavior. `assertEnv()` aborts startup on missing/short/placeholder secrets.
- **CSRF** (`middlewares/csrf.middleware.js`): every state-changing request (non-GET/HEAD/OPTIONS) must carry `X-Requested-With: XMLHttpRequest`. The client's axios instance sends it automatically; cross-site forms can't set it and cross-origin scripts get blocked by CORS. This is what makes `SameSite=None` cookies safe in production.
- **Anti-enumeration**: signin always runs one bcrypt compare (against a dummy hash when the email is unknown) and returns a single generic message; resend-verification returns an identical response for every case.
- **Email verification**: only the SHA-256 *hash* of the token is stored (`select:false`); the raw token lives only in the emailed link. Verifying auto-logs-in and redirects to `CLIENT_URL`.
- **Credentials are per-account, not per-provider**: a Google account starts with no local password and may **add** one through `PATCH /auth/me/password` (no `currentPassword` — there is nothing to prove, and the session cookie is already the authority that lets a Google account delete itself). After that it signs in either way. Every password-gated path therefore keys on the **stored hash**, never on `provider`: the change flow demands the current password once one exists, `forgot-password` resets it, and `deleteMe` starts requiring confirmation. Because the hash is `select:false` and must never travel, `GET /auth/me` returns the derived boolean `hasPassword` (via `User.exists`) — that is what the profile's security card reads to offer "set" vs "change".
- **Rate limiting** (`middlewares/rateLimit.middleware.js`): global backstop plus tighter per-route limits on signin, signup, and email-sending endpoints.
- `sanitizeMongo` strips `$`/`.` operator keys from body & params (defense-in-depth on top of Zod).

### Domain model & fail-closed reference resolution
Mongoose fields are **camelCase**. Core relationships: `Booking` references `User`, `Service`, `City`, and `SpecialRequest[]`. A `Service` is offered in `allCities` or an explicit `cities[]` subset, and accepts `allSpecialRequests` or an explicit `specialRequests[]` subset.

Recurrence is opt-in per service, in the same shape: `recurringEnabled` gates it, and `recurringIntervalDays` optionally pins the exact cadences (empty = the customer picks any whole number of days between `MIN_INTERVAL_DAYS` and `MAX_INTERVAL_DAYS` in `utils/date.util.js` — currently 1–14). `assertRecurrenceAllowed` (booking.service.js) enforces it on **both** paths that can start or continue a plan: the first on-session payment (via `buildValidatedBookingDraft`) and every unattended cycle (via `priceSubscriptionCycle`), so revoking recurrence on a service pauses live subscriptions with `pausedReason: "service-unavailable"` instead of charging on.

**When a booking starts, and for how long.** `bookingTime` is any minute of the clock — 12:20 is a normal arrival time — and `hours` is a **whole or half hour** (1.5 = a 90-minute visit). `utils/duration.util.js` owns both halves of that rule: `isValidDurationHours` (the Zod `hours` bound and the `Booking.hours` validator) and `formatDuration`, which every customer-facing surface uses so a duration never reads as "1.5 h" — the window error, the confirmation email, the admin alert, the invoice line and its PDF. Half is as fine as it gets on purpose: the price is `pricePerHour × hours × cleaners` charged in integer cents, and a quarter hour can't be priced exactly from a per-hour rate.

`assertBookingWindow` (booking.service.js) is the authority on the start time and enforces three rules against the chosen city — start at or after opening, start before closing, and **start + duration** at or before closing — plus "not already past" for a same-day booking. The wizard mirrors all four in `client/src/features/booking/utils/timeWindow.js`: rather than enumerate slots, it validates the typed time and shows the resulting start range ("any time from 09:00 to 16:00"). Because that rule spans two fields *and* fetched city data, it can't live in the flat Zod schema — `ScheduleStep` registers it as a **step guard** (`useStepGuard`, BookingContext) that blocks Continue, so the wizard reports the problem instead of the payment step doing it.

**Multilingual catalogue copy.** Four resources carry customer-facing text per language — `Service` (`name`, `subtitle`, `description`, `includes`), `City` (`name`), `SpecialRequest` and `CleaningTool` (`name`, `description`). One shared implementation, driven by the field lists in `server/utils/translations.util.js`: `models/translations.schema.js` builds the Mongoose path, `validations/translations.validation.js` builds the Zod schema, `normalizeTranslations()` cleans writes. Adding a translatable field is one entry there; adding a language is one entry in `server/utils/locale.util.js` (mirrored by `client/src/i18n/config.js`).

The root fields hold the default locale — still required, unique-indexed, and the source of the public service slug — while `translations` (a `Map` keyed by locale) holds an optional override. Blank values are never stored, so a record states exactly which fields each language covers, and the client resolves **per field** (`client/src/i18n/localizeRecord.js` `localizedField()`): a partly translated record mixes translated and default text instead of falling back wholesale. On PATCH the map is replaced, not merged — an omitted locale is a deletion, an omitted `translations` field changes nothing. The public hooks (`useServices`, `useCities`, `useSpecialRequests`, `useCleaningTools`) cache the raw records and apply the language in a `useMemo`, so switching language re-derives without re-fetching. The admin panel edits all four through the `ResourceModal` `"i18n"` field type (one language at a time), with `features/admin/utils/localizedContent.js` mapping between the form value and the API payload.

Before creating a booking, `booking.controller.js` calls `resolveServiceAndCity` and `resolveSpecialRequests` — these **fail closed**: ids must be valid ObjectIds pointing to existing, `enabled` documents, the city must be within a city-restricted service's coverage, and add-ons must be offered by that service. Controllers never trust raw ids from the request.

**VAT & the B2B reverse charge.** Catalogue prices are **net** — VAT is added on top for whoever owes it. `utils/tax.util.js` turns a catalogue total into what a *given* customer owes, and it is the only place the rule lives. An individual pays the catalogue price plus VAT (`total = net × (1 + rate/100)` — €100 of cleaning at 22% is charged €122); a business whose VAT number Stripe has **verified** against VIES has nothing added and pays the €100 (EU reverse charge). Everything hangs off the single `INVOICE_VAT_RATE` — unset, both treatments collapse to one honest total and the feature is invisible.

The rule is **fail-closed and unreachable by claim**: relief needs `customerType === 'business'` **and** `vatStatus === 'verified'` **and** a stored number, all read from the User document — never from a request body. `vatStatus` is written only from Stripe's verification result, and the tax-profile schema is `.strict()` without that field, so no request shape can set it. `pending` (VIES hasn't answered) and `unverified` are charged VAT: being wrong that way costs a refund request, the other way means under-collecting tax we still owe.

Verification runs through **Stripe Customer Tax IDs** (`services/tax.service.js`) — free, and independent of Stripe Tax, which this codebase does not use: we ask Stripe only "is this a real VAT number?", never "what tax is due". `createTaxId` almost always returns `pending` and the real answer lands minutes later on `customer.tax_id.updated`, so the webhook is what actually flips a business onto the reverse charge; `POST /auth/me/tax-profile/refresh` is the pull-based backstop for a missed delivery.

The treatment is applied at all three pricing points — `buildValidatedBookingDraft` (online), `createBooking` (admin, priced against the **linked** customer, not the admin), and `priceSubscriptionCycle` (**re-resolved every cycle**, like recurrence eligibility, so a lapsed registration starts paying VAT again). It is then **snapshotted** onto `Booking.tax` and carried through promotion, so a profile change between paying and the webhook landing can't restate a completed transaction. An admin edit re-applies the booking's *own* stored treatment rather than the customer's current one. `GET /auth/me` returns the derived treatment so the booking wizard shows the total it is about to charge; the client only applies what the server resolved (`computeQuote`'s `tax` option).

**Cancellation & the late-cancellation fee.** A customer cancelling their own booking (`cancelMyBooking`) gets a **full refund** only when they do it at least `CANCELLATION_WINDOW_HOURS` (default 24 — one day) before the appointment. Inside that window the slot is already burned, so the booking is still cancelled and still refunded, **minus a fee worth one hour of the booked crew**. `utils/cancellation.util.js` owns both halves of that rule so the controller reads as policy rather than arithmetic.

The fee is the booking's labour divided by its `hours`, which — because the total is `pricePerHour × hours × cleaners` plus add-ons — leaves exactly `pricePerHour × cleaners`: an hour of everyone who was going to turn up. Add-ons are **excluded** (a fridge cleaning that never happens costs us nothing), and the labour is recovered by **subtraction** rather than by re-reading the service's current price — the same rule the invoice lines follow, so a catalogue price edit can never restate what was actually charged. Add-on prices are net today and so are grossed up at the booking's own snapshotted `tax.vatRate` before subtraction (a legacy booking with no snapshot was priced when they were inclusive). Anything unreconcilable — an add-on repriced past the labour, references that arrived unpopulated — falls back to an hour's share of the whole charge, which can only ever favour us by the add-ons' share and never exceeds the hour it stands for. A booking of one hour or less therefore keeps its whole charge and Stripe is never called.

The partial refund is a real Stripe partial (`refundBookingPayment(booking, { amount })`, cents, amount folded into the idempotency key) and lands the booking in its own `paymentStatus: 'partially-refunded'` with `refundAmount` recording what went back. That state is deliberately neither `paid` nor `refunded`: money was kept, so `markInvoiceRefunded` is **not** called — the invoice documents a charge that still stands — while a support view must not show a charge that no longer stands in full. `stripeStatus` is left alone too, since Stripe keeps a partially refunded charge at `succeeded` (which is also why the `charge.refunded` webhook's `amount_refunded >= amount` guard already ignores it). The **admin** cancel path is unchanged and always refunds in full — it is the case-by-case escape hatch.

**Invoicing.** Every successful payment issues exactly one `Invoice` and emails it to the customer as a PDF attachment — one-off bookings (`promotePendingBooking`) and every recurring cycle (`sendCycleReceipt`) alike. The single entry point is `issueAndDeliverInvoice(booking, fallback)` in `services/invoice.service.js`, called fire-and-forget so a slow SMTP host can never delay a Stripe webhook.

Two invariants shape the design. **Issuing is idempotent** — the unique `booking` index on `Invoice` resolves the finalize/webhook race the same way `Booking.paymentIntentId` resolves it for the payment, and a duplicate-key collision returns the winner instead of throwing. **Invoicing never breaks a paid booking** — by the time it runs the money has moved, so any failure (numbering, rendering, SMTP) is contained and falls back to the plain `renderBookingConfirmationEmail`; the worst case is the pre-invoice behaviour, never silence.

Tax figures come from `Booking.tax`, not from re-reading the configured rate (`netAmount` is the discriminator — it has no schema default, so its absence means a pre-VAT booking, whose already-collected total is split *inclusively* at the current rate; `invoiceTaxFigures()` owns that fork and hands the same numbers to the totals block and the lines). Line items are stated **net** in both treatments, since catalogue prices already are, so they sum to the invoice's subtotal rather than its total. Under the reverse charge both the PDF and the email carry the Article 196 notice plus the customer's VAT number.

An invoice is a **snapshot, not a set of references**: seller identity, customer details, service name and every priced line are copied in at issue time, so a later catalogue rename or price edit can't restate a document that has already been sent. Line items are reconciled by *subtraction* (net subtotal − resolved add-ons) rather than re-priced from the service, so they always add up to what was actually charged. There is deliberately no update endpoint; the only writes after issue are the delivery stamp and `markInvoiceRefunded` (called from both cancel paths — but only for a *full* reversal — and from the `charge.refunded` webhook, scoped to `status: 'issued'` so redeliveries are no-ops).

Numbers are gap-free per year (`CC-2026-000042`) via an atomic `$inc` on `models/counter.model.js` — `countDocuments() + 1` would collide under concurrency and reuse numbers after a delete. `utils/invoice.util.js` owns the env-driven seller block and the VAT arithmetic: catalogue prices are net, so a configured `INVOICE_VAT_RATE` is applied **exclusively** (`addVatExclusive` — tax on top, gross taken as the sum so `net + vat === gross` to the cent), with `splitVatInclusive` kept only for legacy bookings that carry no snapshot; unset means one honest total and no VAT line. `utils/invoicePdf.util.js` renders with pdfkit at absolute coordinates (the document is created with a near-zero bottom margin so pdfkit's flow-based auto page-break can't spawn a blank page) and probes for a Unicode TTF, because the built-in WinAnsi fonts can't render the el/ka/ru names this product accepts.

The admin panel reads it at `pages/Admin/InvoicesPage.jsx` (list, detail, download, resend); the Bookings page's invoice action calls the idempotent `POST /invoice/booking/:id` with `send: false` and downloads the result, which also covers offline/manual and pre-invoicing bookings. `GET /invoice/:id/pdf` streams the byte-identical PDF the customer was emailed — one renderer, no drift.

**Admin booking alerts.** The same two moments that issue an invoice also tell the team: `promotePendingBooking` (a one-off payment) and `sendCycleReceipt` (every recurring cycle) call `notifyAdminsOfNewBooking` in `services/bookingAlert.service.js`. Both call sites sit on the path that runs **once per booking** — the idempotent returns that resolve the finalize/webhook race are deliberately silent, since a second alert would read as a second booking.

"The admin" is deliberately two things at once, merged into **one de-duplicated email**: every account with `role: "admin"`, read live from the User collection (so the documented promote-in-Mongo step needs no second configuration, and demoting someone stops their alerts), plus the business mailbox from `BOOKING_NOTIFY_EMAIL` → `CONTACT_NOTIFY_EMAIL` → `MAIL_FROM` → `MAIL_USERNAME`. Configured addresses are validated as addresses before use, because that last fallback is a *login* on several hosts. The alert carries what it takes to staff the job without opening the panel — slot, address, duration, notes, and the customer's email/phone as tap-able links — and sets `replyTo` to the customer.

Like the invoice email it is fire-and-forget and **fully contained**: it runs inside a Stripe webhook and the charge worker, and by then the money has moved, so every failure (admin lookup, name resolution, SMTP) is logged and swallowed. Nothing about a paid booking depends on it. Admin-created bookings (`POST /booking`) raise no alert — the admin entering one is already looking at it. Tests pin the mailbox to a known address in `tests/setup/testEnv.js` and select mail by audience (`customerEmails()` / `bookingAlerts()`) rather than by index, since the two sends race.

**Review moderation.** A `Review` belongs to one *completed* booking of its author (one review per booking) and is created with `isPublished: false`. Nothing customer-authored reaches the public site on its own: `GET /review/service/:serviceId` filters on `isPublished: true`, and the only way to flip it is the admin-only `PATCH /review/:id/publish` (`{ isPublished }`, which also stamps/clears `publishedAt`). Editing a review's rating or text resets it to unpublished, so an approved review can't be rewritten into something else that is instantly live. The admin panel drives this from the Quality page's `is_published` switch (`reviewApi.update` → the publish endpoint — the one field the panel may write). Reviews created before the flag existed have no `isPublished` at all and therefore read as hidden; `server/scripts/backfillReviewVisibility.js` publishes them in one pass.

The published ones surface on the service detail page (`features/services/components/ServiceReviews.jsx` via `useServiceReviews`). `GET /review/service/:serviceId` returns a **public projection** — score, text, `createdAt` and a shortened `author` ("Giorgi K."), never the account id/email or the rated booking — plus `reviewCount` and `averageRating` aggregated over *all* published reviews of that service, so the header reads correctly while the list shows six. That aggregate also feeds `aggregateRating` in the page's `serviceSchema`. The section renders nothing when a service has no approved reviews (and stays silent on a failed request) rather than showing an empty state on a sales page.

**Contact messages.** `POST /api/v1/contact` is the API's **only unauthenticated write**, so it carries three independent guards rather than one: `csrfGuard` (a cross-site form can't set `X-Requested-With`), `contactLimiter` (5/hour per IP — `emailLimiter`'s posture, since each accepted message also sends mail), and a **honeypot** field `website` that the client renders off-screen. A filled honeypot returns the ordinary 201 while storing and sending nothing — a distinguishable rejection just teaches the bot which field gave it away, which is also why the field has to be *declared* in the `.strict()` Zod schema.

Order matters: the message is **stored first**, then the team notification is dispatched **fire-and-forget** (`sendEmail(...).catch(...)`, as in `subscription.service.js`) to `CONTACT_NOTIFY_EMAIL` → `MAIL_FROM` → `MAIL_USERNAME`, with `replyTo` set to the customer so the team can just hit Reply. A dead SMTP host, or no configured address at all, costs the notification — never the message. The vocabulary (`CONTACT_TOPICS`, `CONTACT_STATUSES`) lives in `utils/contact.util.js` so the Mongoose enum, the Zod schema and the admin status filter can't drift; `CONTACT_TOPICS` mirrors the dropdown in `client/src/features/contact/validation/contactSchema.js`.

Everything else is admin-only. The customer's text is never editable — the writable surface is `status` (`new`/`handled`, re-stamping `handledAt`/`handledBy` on every transition) and **`POST /contact/:id/reply`**, which emails an answer, appends it to `replies` and marks the message handled in one step. That send is **awaited**, the exact inverse of the arrival notification: the notification is fire-and-forget because the message is already stored, whereas a reply that failed to send must not be recorded as sent — a failure is a 502 with `replies` untouched. `body` is the only accepted field; recipient, subject and the quoted original are all derived from the stored document, so no request shape can redirect a reply at a third party. The panel drives both from `pages/Admin/MessagesPage.jsx` (thread + composer, with a `mailto:` escape hatch for replies that need an attachment). On the client, the contact form's zod messages are **i18n keys** resolved with `t()` at render (`translate()` returns the key when a locale lacks it), and a failed submit shows `pages.contact.errorBody` rather than the API's English-only message.

Mongoose 9 note: document `pre('save')` hooks use the **no-arg form** (no `next` callback) — keeping `next` throws "next is not a function".

## Frontend architecture

Full detail is in `client/FRONTEND.md`; the essentials a future change touches:

- **Feature-driven** layout under `client/src/features/<domain>/` (each colocates `api/`, `hooks/`, `validation/`, `components/`). Shared UI primitives live in `components/ui/` (atomic design), composed by thin page orchestrators in `pages/`.
- **Routing** is a single source of truth: path strings in `constants/routes.js`, route table in `app/router/routeConfig.js` (every page is `React.lazy`). Adding a marketing page = one row + a lazy import.
- **API layer** (`services/api/`): a single axios instance (`withCredentials:true`, base from `VITE_API_BASE_URL`). The `request()` helper **unwraps the `{ data: { data } }` envelope** and interceptors normalize errors to `{ status, message, code, fields }`. Features call `request` + `ENDPOINTS` — never raw axios in components.
- **Client↔server contract is camelCase** end-to-end. `features/booking/api/index.js` `toBookingPayload()` maps wizard fields to the camelCase body the API's `.strict()` schema expects. (Note: FRONTEND.md §7.1 describes a snake_case mapping — that is outdated; the code sends camelCase.)
- **Graceful API degradation** is now limited to the **newsletter** signup, the one form whose endpoint doesn't exist yet: `postWithGracefulFallback` (`features/contact/api/contactApi.js`) simulates acceptance on a 404 or an unreachable API. Booking and contact submissions do **not** — a message that never reached the server is never reported as sent. Delete the helper when `POST /newsletter/subscribe` ships.
- **Legal pages** (`/privacy`, `/terms`) break the i18n rule on purpose. The UI ships in five languages; the documents ship in **two** — `client/src/data/legal/{en,it}.js`, rendered by one `pages/Legal/LegalDocument` component, with the Italian version prevailing. A loosely translated liability clause is worse than an honest label, so `data/legal/index.js` resolves any other locale to English and returns `isFallback`, which the page discloses in a notice; the silent `t()` fallback is exactly what we don't want here. Every operative statement mirrors real behaviour — the late-cancellation fee (`utils/cancellation.util.js`), the VAT/reverse-charge rule, what `DELETE /auth/me` actually deletes — so changing that code means changing both documents. A test pins the two languages to the same structure.
- **Admin panel** (`features/admin/` + `pages/Admin/`) is auth-guarded via `AdminRoute` and consumes the same auth/booking/city/service/user endpoints. The bookings map needs `VITE_GOOGLE_MAPS_API_KEY` (degrades to a setup notice without it).
